The whole lab in one picture

Two CPUs, one variable. Each does read → add 1 → write. If the reads overlap, one increment disappears.

CPU 0 read 100 ⋯ preempted / running user code ⋯ write 101
CPU 1 read 100 ⋯ preempted / running user code ⋯ write 101
Both reads landed in the gap → both writes carry a stale 100 → 2 increments, 1 unit of progress
Entering the kernel is not the same as being atomic. A syscall runs without interruption, but the pair of syscalls has a gap between them, and that gap is where the race lives.

What you actually build

① spinlock (given)

One word + one atomic instruction. Holds for a few cycles.

② semaphore (you write)

A counter + a waiting room. Waits by sleeping, not spinning.

③ two uses (you wire)

As a mutex around a counter, and as counts + mutex around a ring buffer.

Why locking each syscall is useless

Each syscall already runs to completion inside the kernel. The bug isn't inside a syscall — it's between them. The critical section is the pair, so the lock must be taken in user space, around both calls.

Measured when unprotected: final counter=1737 instead of 2000 — 263 increments vanished.

Why the fix works

With a mutex initialised to 1, the first sem_wait takes it (1 → 0) and the other process cannot enter until sem_signal puts it back (0 → 1). The read–modify–write becomes indivisible as a pair.

ucnt_set(0, val + 1);

The spinlock: one indivisible swap

A lock is one word. The safety comes from the fact that "look at it" and "take it" happen in a single instruction.

kernel/spinlock.c — acquire / release
void acquire(struct spinlock *lk) {
  push_off();                                        // interrupts off on THIS hart
  if(holding(lk)) panic("acquire");

  while(__sync_lock_test_and_set(&lk->locked, 1) != 0)  // amoswap.w.aq
    ;

  __sync_synchronize();                              // fence: nothing moves above
  lk->cpu = mycpu();
}

void release(struct spinlock *lk) {
  __sync_synchronize();                              // all stores visible first
  __sync_lock_release(&lk->locked);                  // amoswap.w zero, zero
  pop_off();
}

Why interrupts are not enough

push_off() clears the interrupt-enable bit in this hart's sstatus. The other hart has its own sstatus, its own PC, and is executing the same instructions on the same memory. Your phone going silent does not silence the person next to you.

hart 0
sstatus.IE = 1
hart 1
sstatus.IE = 1
Both harts can still reach the same lock word.

What the fences buy you

After acquire: the fence stops the compiler/CPU from hoisting a critical-section load above the lock point.

Before release: the fence makes every store inside the critical section visible to the next holder before the lock word looks free.

ELI5. One physical key by the door. "Look, then take" must be one motion — otherwise two people both see it hanging and both grab it.

sleep / wakeup: the waiting room

Spinning burns a CPU. Sleeping parks the process on a tag until someone shouts that tag.

kernel/proc.c
void sleep(void *chan, struct spinlock *lk) {
  struct proc *p = myproc();
  acquire(&p->lock);   // process lock FIRST
  release(lk);          // only then drop the condition lock
  p->chan = chan;
  p->state = SLEEPING;
  sched();              // switch to scheduler; p->lock travels with us
  p->chan = 0;
  release(&p->lock);
  acquire(lk);          // return holding lk, exactly as passed in
}

void wakeup(void *chan) {
  for(p = proc; p < &proc[NPROC]; p++) {
    if(p != myproc()){
      acquire(&p->lock);
      if(p->state == SLEEPING && p->chan == chan)
        p->state = RUNNABLE;   // reserve NOTHING
      release(&p->lock);
    }
  }
}

Why a wakeup cannot be lost

The waker holds the same lk. So when it holds lk, the waiter is in exactly one of two places:

Path A — not yet tested. It will acquire lk after the waker releases it, see the new value, and never sleep.
Path B — already SLEEPING. It stored SLEEPING under p->lock, and wakeup() takes that same p->lock before inspecting p->state. So it is guaranteed to be seen.

No third possibility. The mechanical reason: p->lock is acquired before lk is released.

Why the waiter must re-check

wakeup() does three unhelpful things: it wakes everyone on the channel, it reserves nothing, and it does not run the waiter immediately.

So the test must be a while, not an if.

Spin or sleep? (checkpoint 1, part 3)

≈ 10 cycles → spin

Shorter than one swtch(), never mind two switches plus a wakeup() scan of all 64 process slots.

≈ 10,000 cycles → sleep

On total system cycles, the spinning CPU could instead be running the process that frees the resource.

Assumptions to say out loud: (1) the holder can actually run — on a uniprocessor with interrupts off, spinning deadlocks; (2) "cheaper" means system-wide cycles, not this process's latency; (3) 10 and 10,000 are illustrative magnitudes, not measured xv6 thresholds.

The semaphore: a counter with a waiting room

A spinlock protects a few instructions. A semaphore lets a process sleep until a resource exists.

kernel/semaphore.c — the object
#define MAX_SEMAPHORES 32

struct semaphore {
  struct spinlock lock;   // condition lock
  int value;              // units available
  int in_use;             // slot allocated?
};

struct semaphore semaphores[MAX_SEMAPHORES];
struct spinlock sem_table_lock;  // guards the table
the three "inits" — exam favourite
sem_init(value)   user.h    a SYSCALL
sys_sem_init()    sysproc.c handler: argint then sem_alloc
sem_alloc(value)  semaphore.c allocator: find free slot
seminit()         semaphore.c BOOT setup, called from main()
                                returns nothing, hands out nothing
the implementation you write
int sem_wait(int semid) {
  if(semid < 0 || semid >= MAX_SEMAPHORES || !semaphores[semid].in_use)
    return -1;

  struct semaphore *sem = &semaphores[semid];

  acquire(&sem->lock);
  while(sem->value == 0)          // re-check: wakeup reserves nothing
    sleep(sem, &sem->lock);       // channel == the semaphore's ADDRESS
  sem->value--;                   // decrement INSIDE the lock
  release(&sem->lock);

  return 0;
}

int sem_signal(int semid) {
  if(semid < 0 || semid >= MAX_SEMAPHORES || !semaphores[semid].in_use)
    return -1;

  struct semaphore *sem = &semaphores[semid];

  acquire(&sem->lock);
  sem->value++;
  wakeup(sem);                    // increment + wakeup = one atomic step
  release(&sem->lock);

  return 0;
}

What sem_basic() proves — and what it doesn't

Proves: the sequence 1 → 0 → 1, and that sem_free succeeds.

Never exercises: sem_wait on a zero value — so no sleep(), no wakeup(), no re-check loop, no sched(). It is single-threaded, so no contention. It also skips two-waiters-one-signal, table exhaustion, the -1 paths, and freeing a semaphore that still has users.

A passing test only proves what it exercises. Opening and closing a door proves the handle turns; it says nothing about forty people pushing at once.

When is sem_free() safe?

sem_free() only clears in_use. It neither wakes nor waits for users. So it is safe only when no process can still call wait/signal on that id:

  • in race_test(): after wait(0) has reaped the child;
  • in producer_consumer(): after all 96 reads and both producers reaped.

Free too early and the slot gets reused — a sleeper on the old channel would wake on, or decrement, the new semaphore.

Producer / consumer: a 16-slot ring

Two producers, one consumer, three semaphores. Step through it and watch the counters move.

the rule

Why counts alone are not enough

A counting semaphore controls how many may be inside — not who may overlap with whom on shared indices.

  • two producers both pass sem_wait(empty) and both write data[tail] with the same tail → one byte silently overwritten, tail advanced twice;
  • two readers both take a filled token and read the same slot → duplicate byte;
  • a reader reads data[head] while a writer is midway through.
Condition counts and mutual exclusion are different jobs. You need both.

Why empty/filled come before mutex

A free slot is only created by the consumer calling sem_signal(empty) — and the consumer can only reach that after ubuf_read(), which requires mutex.

the cycle if you take mutex first
producer: holds mutex, waits for empty
consumer: waits for mutex, which is needed to create empty
          └── circular wait ── deadlock
Rule: never hold a lock while waiting for a resource whose release requires that lock.

What the test actually proves

the supplied assertion
T_ASSERT(valid[(unsigned char)tmp]);

It only checks that each received byte is one of the characters in msg. It does not count occurrences, does not check order, and cannot detect a duplicated, lost, or reordered byte.

what a pass establishes

No corrupted or foreign byte appeared, and the run completed without deadlock.

The stronger correctness argument comes from the design (counts + mutex), not from the test. Being able to say this is the checkpoint.

How a sem_wait() reaches the kernel

Five layers. Only the last one is a semaphore; everything before it is plumbing.

stub entry("sem_wait") in user/usys.pl → generates usys.S: li a7, 27; ecall ecall

Checkpoint 1 — Explain the synchronization mechanisms

  1. Compare spinning and sleeping costs, stating your assumptions.

    Show answer
    • ≈10 cycles: spin. A context switch costs far more than the whole wait, so sleeping loses.
    • ≈10,000 cycles: sleep. Burning a hart that long wastes a CPU another process could use.
    • Assumptions to state: the holder can make progress (not descheduled or blocked on us); the comparison is system-wide throughput, not one thread's latency; the cycle counts are illustrative magnitudes, not measurements.

  2. Identify the condition lock, wait channel, and process lock in the sleep/wakeup path.

    Show answer
    ElementIn the codeRole
    condition locklk, passed by the callerprotects the condition being tested (ticks, buffer counts); released inside sleep()
    wait channelchan, an arbitrary address such as &ticksa tag matching sleepers to the waker; wakeup() compares it
    process lockp->lockprotects process state and the run queue; taken before lk is dropped

    Order: caller holds lk → sleep() takes p->lock → releases lk → sched() switches away holding p->lock.

  3. Explain why a woken process must recheck its condition.

    Show answer
    • wakeup(chan) wakes every process sleeping on that channel, and reserves nothing.
    • The condition that made the first waiter sleep may already have been consumed by another waiter, so being awake does not mean the condition holds.
    • Hence while(condition) sleep(chan, lk); — never if. With if, a woken-but-unlucky waiter proceeds anyway and the resource count goes negative.

  4. Explain why separate reads and writes cannot replace atomic lock acquisition.

    Show answer
    • Atomic version: __sync_lock_test_and_set(&lk->locked, 1) compiles to one amoswap.w.aq — read-and-take is a single indivisible step.
    • Read-then-write version: two harts can both read locked == 0, both conclude the lock is free, both write 1, and both enter the critical section.
    • intr_off() does not fix it: push_off() clears only this hart's sstatus; the other hart keeps running and still races.
    • Interrupts-off gives per-hart atomicity, which is exactly what you need around the atomic instruction — not mutual exclusion between harts.

Checkpoint 2 — Explain the semaphore implementation

  1. Distinguish user sem_init(), boot-time seminit(), and kernel sem_alloc().

    Show answer
    NameWhereWhat it really is
    sem_init(value)user/user.ha syscall the user calls; returns a semid or -1
    seminit()kernel/semaphore.cboot-time setup: initialises the table and its lock once, before any process runs
    sem_alloc(value)kernel/semaphore.cthe allocator: takes sem_table_lock, finds a free slot, sets in_use = 1, stores the value, returns the index

    The kernel handler sys_sem_init() sits between the syscall and sem_alloc(). Two of these names being similar is the exam trap.

  2. Explain which lock and channel your wait and signal operations use.

    Show answer
    • Lock: the per-semaphore sem->lock, so different semaphores never contend. sem_table_lock guards only allocation, not waiting.
    • Channel: &semaphores[semid], so wakeup() reaches only the waiters of this semaphore.
    • sem_wait(): acquire(&sem->lock) → loop → decrement → release().
    • sem_signal(): acquire(&sem->lock) → value++ → wakeup(&semaphores[semid]) → release().
    • sem_getvalue() reads value under the same lock, so you never see a half-updated state.

  3. Explain why a woken waiter must recheck that the semaphore value is positive before decrementing it.

    Show answer
    • sem_signal() wakes all sleepers on the channel, and the token is not reserved for any of them.
    • When two waiters race for one token, the first decrements it to 0; the second must see 0 and sleep again.
    • So the test is while(sem->value == 0) sleep(...). With if, the second waiter decrements past zero and value becomes -1 — a signal that was never sent, and mutual exclusion is broken.

  4. Show the basic count sequence passing and identify what that test leaves untested.

    Show answer
    • Passes: sem_init(1) → sem_wait brings 1 → 0 without blocking → sem_signal restores 0 → 1. So the happy path, including the value arithmetic, works.
    • Untested: the zero-count path — no waiter ever has to sleep(), so the blocking code, the while re-check, and the wakeup are never exercised.
    • Also untested: contention between processes. That is what Part 3 and Part 4's two-producer run supply.

  5. Explain when it is safe for these exercises to free a semaphore.

    Show answer
    • Only when no process can still use that id: in these exercises, after the parent has wait()-ed for every child that shares it.
    • Freeing earlier clears in_use, so the slot can be handed to a new sem_init(). A straggler then decrements a different semaphore — a bug that looks like random corruption rather than a race.
    • Order to state: all producers/consumers done → wait(0) for each child → sem_free().

Checkpoint 3 — Defend the critical section

  1. Demonstrate a lost update using two processes' reads and writes.

    Show answer
    parent: val = ucnt_get(0);      // reads 100
child:  val = ucnt_get(0);      // reads 100  ← same value
parent: ucnt_set(0, val + 1);   // writes 101
child:  ucnt_set(0, val + 1);   // writes 101  ← increment lost

    Two increments, counter up by one. The unprotected run shows a total below 2 × N, e.g. 1737 != 2000.

  2. Explain why protecting the two system calls separately is insufficient.

    Show answer
    • The invariant is “the value I read must still be the value I write”, and it spans both calls.
    • A lock inside ucnt_get and another inside ucnt_set makes each call atomic but leaves the gap between them open — which is exactly where the interleaving above happens.
    • Two operations being individually atomic does not make the pair atomic. The critical section must enclose the whole read-modify-write.

  3. Show the expected final count and identify the semaphore shared by parent and child.

    Show answer
    • Expected: 2 × N — with N = 1000 that is 2000. Every increment must survive.
    • The shared semaphore: created by sem_init(1) before fork(), so the child inherits the same semid.
    • That semid is an index into one kernel table, so parent and child reach the same struct semaphore — including its lock and channel — even though they are separate processes with separate address spaces.
    • Value 1 makes it a binary semaphore usable as a mutex.

  4. Explain why the parent waits before validating and freeing the semaphore.

    Show answer
    • To validate: the total is only final after both children have finished. Reading earlier compares against a count that is still growing.
    • To free: the parent must not free a semaphore while a child could still be inside sem_wait/sem_signal; wait(0) guarantees no users remain.
    • So one wait(0) does both jobs: it completes the arithmetic and establishes the safe moment to sem_free().

Checkpoint 4 — Explain coordination and progress

  1. Explain each semaphore's role and derive its initial value from the empty buffer.

    Show answer
    SemaphoreRoleInitialDerivation

    filledcounts readable bytes0nothing has been produced, so a consumer must block

  2. Trace the semaphore and buffer calls used to produce one byte and consume one byte.

    Show answer
    Producer: sem_wait(empty) → sem_wait(mutex) → ubuf_write() (advances tail) → sem_signal(mutex) → sem_signal(filled)
    Consumer: sem_wait(filled) → sem_wait(mutex) → ubuf_read() (advances head) → sem_signal(mutex) → sem_signal(empty)
    • Order matters: take mutex after the slot is guaranteed. A producer that grabs mutex first then waits for empty deadlocks the consumer out.
    • The yield() calls inside kernel/ubuf.c widen the window between read and write of the indices, so an unprotected index update is actually observable.

  3. Explain why counting available slots alone does not protect the buffer's shared indices.

    Show answer
    • empty/filled enforce capacity — how many slots may be written or read. They say nothing about who may touch head and tail.
    • With two producers, both could pass sem_wait(empty) and then compute the same tail, writing to the same slot: one byte silently lost.
    • The index update is itself read-modify-write, so it needs mutex. Counts and mutual exclusion do different jobs; neither replaces the other.

  4. Show completion with both producers reaped and the semaphores freed.

    Show answer
    • Two producers send 48 bytes each = 96 bytes through the 16-slot ring.
    • The parent consumes until it has read 96 bytes, so it cannot exit early; the test then prints [producer_consumer] PASS: message delivered.
    • Reap: two wait(0) calls, one per producer, so no child is left running.
    • Free: three sem_free() calls — empty, filled, mutex — only after the reaping.
    • Final invariant to quote: empty 16 + filled 0 + in-hand 0 = 16.

  5. State the limits of the supplied character-membership check.

    Show answer
    • The consumer checks that each received byte belongs to the character set present in msg. That is membership only.
    • It does not compare the received stream with the expected sequence, so it cannot prove the absence of duplication, loss, or reordering — a duplicated byte from the same alphabet still passes.
    • Combine the pass with your argument about counts, mutual exclusion, and operation order; do not claim the test alone proves correctness.

Traps that cost marks not from the manual

Show the six traps
  • Using if instead of while in sem_wait → value goes negative.
  • Decrementing value outside the lock → lost update inside the semaphore itself.
  • Calling wakeup() after release(&sem->lock) → waiter can miss the wakeup.
  • Taking mutex before empty/filled → deadlock.
  • Freeing a semaphore before wait() → slot reuse, someone decrements the new semaphore.
  • Claiming the test proves correctness — it proves only membership and completion.

One-screen revision card

If you remember nothing else, remember these shapes.

spinlock

  • locked is one word
  • amoswap = read+trade in one instruction
  • push_off is per-hart: no cross-CPU exclusion
  • fence after acquire, before release

sleep / wakeup

  • chan is a tag, not storage
  • take p->lock before dropping lk
  • wakeup wakes all, reserves nothing
  • hence while, never if

semaphore

  • value + per-sem lock + in_use
  • channel = the semaphore's address
  • decrement/increment inside the lock
  • free only after all users are gone

mutex use

  • sem_init(1)
  • wrap the read–modify–write pair
  • fork copies the index, not the table
  • wait(0) before reading the total
