Sv39: split one virtual address

A 64-bit virtual address is treated as three 9-bit filing-cabinet indexes plus a 12-bit byte offset.

L2 index · 9 bits
101010101
L1 index · 9 bits
010101010
L0 index · 9 bits
111000111
offset · 12 bits
0000 0000 0100
L2: choose which entry in the root page table to inspect.

How do I calculate the indexes?

“Next bit” means the next group of bits when reading from the right-hand side. We do not take one bit at a time: after the 12 offset bits, take the next 9 bits for L0, then the next 9 for L1, then the next 9 for L2.

offset = (VA >> 0) & 0xFFF
L0 = (VA >> 12) & 0x1FF
L1 = (VA >> 21) & 0x1FF
L2 = (VA >> 30) & 0x1FF

>> moves the wanted bits to the right edge. & keeps only the required number of bits: 0xFFF keeps 12; 0x1FF keeps 9.

Why start on the right? The bottom 12 bits are the byte position inside a page. Page-table lookup happens for the page, so those offset bits are used last.
Memory phrase: strip off 12, then read 9, then 9, then 9.

Worked example: VA = 0x52345678

Write the address as 39 bits and put separators at the boundaries:

000000001 010010001 101000101 011001111000

000000001₂ = 1

010010001₂ = 145

0x678 = 1656
Example L1:
010010001₂

12 offset bits

A page is 4096 bytes = 2¹², so the bottom 12 bits choose the byte inside the page.

9 bits each

One page holds 4096 / 8 = 512 PTEs = 2⁹ entries, so each level needs 9 bits.

39 total bits

9 + 9 + 9 + 12 = 39. xv6 uses the low half; bits 63–39 must be zero.

PTE flags: the key card

PPN bits → physical frame number
permission flags
V validR readW write X executeU user
V only is special. A PTE with PTE_V but no R/W/X is not a data page — it points to another page-table level.

Page faults: classify before allocating

A fault is not automatically “please give me a page.” The kernel must decide whether the address is a valid lazy hole, a protected page, or nonsense.

The three-way test in code

if (va < p->sz && va < MAXVA) {
  pte = walk(p->pagetable, va, 0);
  if (pte == 0 || (*pte & PTE_V) == 0)
    lazy = 1;                 // reserved, but no mapping yet
}

if (lazy)
  kalloc() + memset() + mappages(..., PTE_W|PTE_R|PTE_U);
else
  setkilled(p);               // guard page or wild address
Important: sepc is not advanced. After the new PTE exists, the faulting instruction is retried and succeeds.
05

First touch: repair the missing mapping

This is the exact lifecycle of writing to a reserved but unmapped heap page.

ready
1
User instruction: store to address 0x8000.
2
Hardware trap: scause 15 (store page fault), stval = 0x8000.
3
Classify: address is below p->sz, and its PTE is absent.
4
Allocate: kalloc() gets a frame; memset() zeros it.
5
Map: mappages() installs a leaf PTE with R|W|U|V.
6
Return: sepc stays unchanged, so the original store is retried.
physical frames
4
PTE for 0x8000
absent

Why zero the frame?

A newly allocated physical page may contain old bytes from another process. memset(mem, 0, PGSIZE) prevents the new user page from exposing stale data.

Why map the rounded address?

stval may point anywhere inside the page. PGROUNDDOWN(va) finds the page boundary so the whole 4096-byte page gets one PTE.

done

countvp()

return PGROUNDUP(myproc()->sz) / PGSIZE;

A partly used final page still counts as one virtual page.

countpp()

pte = walk(p->pagetable, a, 0);
if (pte == 0 || !(*pte & PTE_V)) continue;
if (PTE_FLAGS(*pte) == PTE_V) continue;
n++;

Count only valid leaf mappings; skip missing tables, holes, and non-leaf entries.

  2. Explain what walk() may allocate and how that differs from allocating heap data.

    Show answer
    • With alloc = 1, walk() may kalloc() page-table pages — bookkeeping that stores PTEs — and marks the parent entry PTE_V only.
    • Heap data comes from an explicit kalloc() in uvmalloc(), whose frame is then installed as a leaf PTE with R|W|U.
    • So walk() builds cabinet shelves; it never puts the document in the drawer. Counting one as the other is a real bug.

  3. Trace a positive sbrk() request and identify where eager allocation occurs.

    Show answer
    ecall → syscall() → sys_sbrk() → growproc(n) → uvmalloc() → kalloc() + memset + mappages()

    Eager allocation happens inside uvmalloc()'s loop: one kalloc() per page, before the program has touched anything. That is why PP rises together with VP at the moment sbrk() returns.

Checkpoint 2 — Defend the page and frame counts

  1. Explain the counting boundary and the treatment of the guard page.

    Show answer
    • Boundary: both counters describe [0, p->sz), rounded up to a page — code, data, heap, user stack, and the stack guard page.
    • Guard page: exec() allocates USERSTACK+1 pages and calls uvmclear() on the lowest, clearing PTE_U but keeping PTE_V and the frame.
    • So the guard page is counted by countpp(): the frame exists and must later be freed, even though user mode cannot touch it.
    • Excluded: page-table frames, plus TRAMPOLINE and TRAPFRAME, which sit near MAXVA, far above p->sz.
    • This is why the counter uses raw walk(): walkaddr() rejects !PTE_U and would drop the guard page.

  2. Show that lazytest reaches your system calls rather than its former placeholders.

    Show answer
    • The supplied lazytest.c used to define its own countvp()/countpp() returning 0. While they exist, the compiler binds the calls to them and your kernel handlers never run.
    • Fix: delete both placeholder definitions from lazytest.c. The only remaining definition is the generated stub in usys.S, produced from entry("countvp") in usys.pl.
    • Evidence it reached the kernel: the output prints Before: VP=4, PP=4. Placeholders would print VP=0, PP=0.
    • Second piece of evidence: usys.S now contains li a7, SYS_countvp / SYS_countpp, and syscalls[] in syscall.c has entries at those numbers.

  3. Explain the eager-allocation counts within one run of the test.

    Show answer
    Before: VP=4, PP=4
After sbrk(122880): VP=34, PP=34      ← eager: both rise
After touching: PP=34                 ← no change, nothing was left to fault
    • Before 4/4: two program pages (text/data), one guard page, one user stack page (USERSTACK is 1). PP = VP because every page is backed.
    • After sbrk: +30 virtual pages and +30 frames at once, because uvmalloc() mapped them all.
    • After touching: unchanged — the pages were already mapped, so no faults occur.
    • Quote this as the flaw the lab removes: 30 frames are committed before a single byte is used.

Checkpoint 3 — Explain the fault path

  1. Demonstrate a load or store fault and distinguish its address from the instruction address.

    Show answer
    • Run fault read or fault write in the xv6 shell. Both must terminate the process.
    • stval = the faulting data address — the memory the load or store tried to reach.
    • sepc = the faulting instruction address — the program counter of the lw/sb that caused it.
    • scause tells you which: 13 load page fault, 15 store page fault.

    Say it as: stval is what it touched, sepc is where it stood.

  2. Explain why fault selects an unallocated page and how its printed target relates to the kernel diagnostic.

    Show answer
    • fault.c calls sbrk(0), which only reports the break — n == 0 changes nothing, so no space is reserved.
    • It then targets PGROUNDUP(end): the first page boundary at or past the break, which is outside the process.
    • The printed target is exactly the value that appears as stval in the kernel's diagnostic — same address, one from user space and one from the trap.
    • Because va >= p->sz, this stays invalid even after lazy allocation: it must be killed, never repaired.

Checkpoint 4 — Explain allocation on demand

  1. Show reservation without immediate physical allocation, followed by allocation on first touch.

    Show answer
    Before: VP=4, PP=4
After sbrk(122880): VP=34, PP=4      ← reserved only
After touching: PP=34                 ← one frame per first touch
    • In growproc(), the n > 0 branch stops calling uvmalloc() and only moves p->sz.
    • The first load or store to each reserved page faults; usertrap() allocates one zeroed frame and maps it.
    • VP rises by 30 immediately; PP rises one at a time as pages are touched.

  2. Explain how the handler distinguishes a missing heap page from a protection fault.

    Show answer

    All three conditions must hold for a lazy repair:

    scause == 13 or 15
    va = r_stval();   va < p->sz  &&  va < MAXVA
    pte = walk(p->pagetable, va, 0);   pte == 0 || !(*pte & PTE_V)
    CaseTest resultAction
    untouched heap pagebelow p->sz, no valid PTEallocate + map + retry
    stack guard pagePTE valid but PTE_U clearedkill — it is protection, not absence
    wild pointerva >= p->szkill — never promised

    The distinction is absence inside the promise versus presence with denied permission or outside the promise.

  3. Explain why a repaired page fault retries the same instruction.

    Show answer
    • The trap saved the user PC in the trapframe, and usertrapret() restores it into sepc.
    • usertrap() never advances sepc, so sret returns to the same lw/sw.
    • On the retry the PTE exists, translation succeeds, and the access completes — the program never observes the fault.
    • If you advanced sepc, you would skip the access: the write would silently vanish and the register would hold garbage.

  4. Show that a partially touched heap can be released without a panic.

    Show answer

    Reserved-but-untouched pages are normal, so uvmunmap() must skip them:

    SituationMeaningAction
    walk(..., 0) == 0no lower page table existscontinue
    !(*pte & PTE_V)empty leaf slotcontinue
    PTE_FLAGS(*pte) == PTE_Vvalid non-leaf where a leaf was expectedpanic — structural bug

    Demonstrate by touching a few pages, then calling sbrk(-n) or exiting: the hole pages are skipped, the mapped ones are freed, and no panic appears. The old code panicked on exactly these holes.

  5. State why lazy allocation saves memory when reserved pages remain unused, and identify the test's limits.

    Show answer
    • Why it saves: a frame is committed only for a page that is actually touched. Unused reserved pages cost p->sz arithmetic and nothing else, so a process can reserve a large heap cheaply.
    • Limit 1: lazytest touches every page, so its own run ends with PP = VP — it proves the timing of allocation, not long-run savings.
    • Limit 2: the final Success: PP count increased after touching pages is a false positive on an eager kernel: the check is pp_after_touch - pp_before >= 30, which is 34 - 4 from the sbrk() moment. Only the After sbrk line proves laziness.
    • Limit 3: the test says nothing about fragmentation, swapping, or multi-process pressure.

Optional discussion — Stack growth

  1. How would you recognize legitimate downward stack growth, allocate new stack pages, and retain a guard page that detects overflow? Relate your answer to the fixed stack and guard-page setup in exec().

    Show answer
    • Recognise: a store fault whose address is just below the current stack bottom, within a bounded window (say one page plus slack), and strictly above the guard page. Compare against a stored stack-low bound, not against p->sz, which also covers the heap.
    • Allocate: kalloc(), zero, mappages() with R|W|U, and move the stack-low bound down — one page at a time, exactly like the heap repair.
    • Retain the guard: never allocate the page at or below the guard address. A fault inside the guard page means overflow, so kill rather than grow; otherwise the guard is defeated and overflow silently corrupts data.
    • In exec(): the stack is fixed — USERSTACK+1 pages are mapped and uvmclear() clears PTE_U on the lowest, which is why the current design cannot grow at all. Adding growth means tracking a stack-low bound in struct proc and bounding total growth.

    This is a discussion question, not a code requirement — say the mechanism and the guard-page rule, and stop.

Traps that cost marks not from the manual

Show the five traps
  • Allocating a frame for every fault without checking va < p->sz turns wild pointers into valid memory.
  • Allocating over a present guard PTE turns stack overflow into silent corruption.
  • Counting page-table frames as process frames confuses the cabinet with the room.
  • Using walkaddr() for countpp() drops the guard page because it has no PTE_U.
  • Advancing sepc skips the user's instruction instead of retrying it.
